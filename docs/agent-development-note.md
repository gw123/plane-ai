# Agent 扩展开发心得

> 这是一份偏实践的开发心得，强调如何与 AI 协作做复杂功能开发。正式约束以 `docs/agent-development-spec.md` 为准。

## 1. 为什么复杂任务容易发散

在一个长对话里持续推进复杂任务，AI 往往会在前几步表现得很完整，但到了第三、第四步之后，容易出现下面的问题：

- 上下文越来越长，重点被稀释
- 中途新增想法越来越多，边界逐渐模糊
- “顺手优化”变多，主目标开始失焦
- 最后虽然做了很多事，但结果偏离最初要解决的问题

所以，复杂任务不能只靠“多聊几轮”推进，而要靠更强的阶段约束来保持收敛。

## 2. 推荐工作方式

### 2.1 先拆 Sprint，再拆 Issue

- 大任务先拆成 Sprint
- Sprint 只定义阶段目标、范围和验收标准
- Sprint 下面再拆成多个 Issue
- 每个 Issue 必须是一个独立、可交付、可验收的最小单元

这样做的核心价值是：让 AI 每次只聚焦一个小目标，而不是一直背着整个大任务往前走。

### 2.2 每个 Issue 只做一件事

一个 Issue 最好只承载一个主目标，例如：

- 只补齐数据结构
- 只补齐接口
- 只完成页面展示
- 只补测试或验收

不要把“修复 + 重构 + 优化 + 顺手增强”混在一个 Issue 里，否则上下文很快会失控。

### 2.3 完成一个 Issue 就回到 Sprint 做 Review

每完成一个 Issue，都要检查：

- 这次结果是否仍然服务于 Sprint 目标
- 有没有出现额外复杂度
- 有没有偷偷扩大范围
- 下一个 Issue 是否仍然成立

Review 的目的不是重复检查代码，而是防止整体方向漂移。

### 2.4 Review 要主动检查“实现和文档是否漂移”

Review 不能只看“功能是不是跑起来了”，还必须检查：

- 当前实现是否仍然符合冻结 contract
- 当前实现是否仍然符合 architecture 里定义的边界
- 当前代码里的类型、接口、返回结构，是否已经和文档语义发生漂移

这是一个很容易被忽略的问题，因为很多漂移在短期内不会立刻报错：

- 类型还能通过
- 页面还能运行
- build 也可能正常

但如果这时候继续往下做后续 Issue，就会把漂移一起带到后面，最后形成“实现看起来在推进，但目标其实已经悄悄变了”的坏情况。

这次就是一个明确的 bad case：

- `/Users/gaowei7/code/js/plane/packages/services/src/ai/agent.service.ts`
  - `listConversations` 同时兼容数组和 `{ results }`
  - 这说明实现和文档里的列表返回结构没有真正收敛到一个版本
- `/Users/gaowei7/code/js/plane/packages/services/src/ai/agent.service.ts`
  - `getConversation` 按平铺对象 + `messages` 消费
  - 但 contract 示例里写的是 `{ conversation, messages }`
- `/Users/gaowei7/code/js/plane/packages/types/src/agent.ts`
  - `IAgentToolCall.status` 被收窄成 `"completed" | "failed"`
  - 但 contract 里定义的是 `"pending" | "running" | "completed" | "failed"`

这些问题在当下不一定马上把功能做坏，但它已经说明：

- 代码实现
- 前端类型
- 冻结文档

三者没有保持同一个事实来源。

更严重的问题不是“有一点不一致”，而是如果此时继续做 U7 / U8：

- 后续实现会建立在漂移后的事实之上
- review 会越来越难判断“到底谁是准的”
- 最后要么返工前面，要么被迫修改冻结文档去迁就已有实现

所以，Review 阶段必须把“实现和文档漂移检查”当成一个显式步骤，而不是顺手看一下。

更稳的做法是：

- 每次 Review 至少抽查一遍：
  - contract
  - architecture
  - 当前 Issue 涉及的 service / types / API
- 发现漂移后，不要直接继续后续 Issue
- 先明确是：
  - 文档要改
  - 还是实现要改
- 在没有统一之前，不允许带着双轨事实继续往下开发

一句话说清楚：

**功能对了不等于方向对了；Review 必须及时发现“代码已经和文档不是同一个东西”这种漂移。**

### 2.5 明确执行约束：坚决不容忍“双轨事实共存”

这次复盘后，有一条必须单独写死的执行约束：

**冻结文档一旦存在，就只能保留一个事实版本；坚决不允许为了“先跑起来”而容忍双轨事实共存。**

这里的“双轨事实共存”包括但不限于：

- service 层同时兼容两种返回结构，例如“数组”和 `{ results }` 并存
- 前端类型写的是一种语义，后端接口返回的是另一种语义
- contract 写的是一种字段集合，实现里却偷偷收窄或改语义
- review 已经发现漂移，但实现继续建立在漂移后的事实之上往前推进

必须执行下面几条规则：

1. **文档优先，不实现优先**  
   只要 `contract` / `architecture` 已冻结，就必须把它当成唯一事实源；不能先看当前代码“怎么跑”，再决定文档算不算数。

2. **发现漂移先停，不做兼容层兜住**  
   发现“文档是一套、实现是一套”时，第一动作不是补兼容，而是先停下来判断到底谁应该改。

3. **没有明确兼容期，就不允许双写/双读/双消费**  
   除非文档里显式写了兼容窗口、迁移路径和清理时间点，否则：
   - 不允许 service 同时兼容两种响应 shape
   - 不允许类型同时表达两个互相冲突的语义版本
   - 不允许前端为了接当前实现而绕开冻结 contract

4. **文档不满足要求或文档有误时，先和用户对齐，再开发**  
   如果发现：
   - 文档缺字段
   - 文档语义不完整
   - 文档示例明显和真实业务冲突
   - 文档本身有错误

   那就必须先回到用户，确认应该改文档还是改实现；在对齐完成前，不允许直接进入开发。

5. **类型层和服务层负责“收敛”，不能负责“和稀泥”**  
   `types` 和 `service` 的职责是把事实收敛到冻结 contract，而不是通过“同时兼容旧版/新版”把漂移继续往后传。

一句话定规矩：

**一旦发现双轨事实，就必须收敛；不能为了短期推进速度，把不一致包装成兼容能力继续带着往前做。**

### 2.5 新 bug 默认开新对话，除非它仍是当前 Issue 的直接子问题

这次协作里，一个很具体的问题是：bug 到底应该在当前对话继续修，还是新开对话。

更稳的做法不是“永远开新对话”，也不是“尽量沿着当前对话一直修”，而是按下面规则切：

- **默认：新 bug 开新对话**
- **例外：当前 Issue 的直接 Review finding，且仍在同一轮修复里，可以留在当前对话继续**

这样做的原因很直接：

- 当前对话越长，AI 越容易继承旧假设
- 新 bug 往往意味着新的目标、边界和验证方式
- 如果不主动切对话，AI 很容易把“当前修复”和“新的返工项”混在一起做

什么时候可以留在当前对话：

- bug 是当前 Issue 的直接 Review finding
- 当前 Issue 还没有结束
- 一次只修一个 finding
- 修复仍然满足“单问题、最小改动、最小验证”

什么时候必须开新对话：

- bug 已经不属于当前 Issue，而是新的缺陷单
- 当前 Issue 已经 Review 通过，或者已经进入提交后的下一阶段
- 修复这个 bug 需要重新定义目标、非目标或验收标准
- 发现 contract / architecture / 实现存在漂移，需要先重新对齐
- 当前对话已经明显过长，AI 速度下降、结论开始依赖旧上下文

一句话定规则：

**当前 Issue 的收尾修复可以留在当前对话；任何新的 bug 单默认都应该开新对话。**

## 3. 如何更好地和 AI 一起开发

### 3.1 先让 AI 复述，再让 AI 开始写

不要一开始就让 AI 写代码，先让它复述：

- 当前目标是什么
- 这次不做什么
- 计划修改哪些地方
- 如何验证完成

先对齐，再执行，能明显减少跑偏。

### 3.2 给 AI 的任务要小、清楚、可验收

更适合 AI 的任务描述方式是：

- 本次只做什么
- 不要做什么
- 修改范围在哪里
- 完成标准是什么
- 如何验证

不要只说“把这个功能做完”，这种说法对复杂任务几乎必然会发散。

### 3.3 中途的新想法不要当场吸收

开发过程中经常会冒出一些“这个也可以顺手做”的想法。

这类内容不要直接塞进当前 Issue，而是应该统一记录到一个“建议去做”清单里：

- 先记录
- 不立即执行
- 当前任务完成并 Review 通过后，再决定是否开启新的迭代处理

这样既不会丢掉想法，也不会破坏当前任务的收敛性。

### 3.4 前端高不确定性任务，先做主链路，不做工程补强

前端任务很容易比后端任务更发散，尤其是下面几类场景：

- 首次接入新库
- 同时改 UI、状态、协议适配
- 需要真实异步链路才能验证
- 交互策略还没完全定型

这类任务最容易出现的问题是：主功能还没完全站稳，就顺手把很多“工程上应该补”的东西也一起做了。

例如：

- 空线程清理
- 失败回滚
- 重试和取消
- 文案优化
- 细颗粒 loading 状态
- 缓存和预加载
- 容错兼容和埋点

这些内容不是不该做，而是不应该和“主链路落地”混在同一个 Issue 里一起做。

更稳的做法是：

- 当前 Issue 只做最小 happy path
- 只验证主链路是否成立
- 工程补强统一记到“建议去做”清单
- 当前 Issue Review 通过后，再单独拆新 Issue 处理补强

一句话说清楚：

**高不确定性前端任务，先证明它能跑通，再补工程质量；不要在第一次落地时同时做两件事。**

### 3.5 新 bug 对话为什么必须带模板

新 bug 如果只是把报错贴给 AI，通常会有几个风险：

- AI 会自动继承上一个任务里的隐含前提
- AI 会默认沿着旧的范围继续扩展
- AI 会把“真正的 bug 修复”和“顺手优化”混在一起
- 最后虽然修了一些东西，但不一定对准当前缺陷

所以，新 bug 对话必须显式带模板，至少把下面几件事说清楚：

- 这是一个新的 bug 修复任务
- 当前 bug 是什么
- 以什么文档或契约为准
- 预期行为是什么
- 这次不做什么
- 允许改哪些地方
- 怎么验证

模板不是为了形式，而是为了强制 AI 在开始前重新收敛一次事实边界。

推荐模板：

```text
这是一个新的 bug 修复任务，不继承上一个任务的隐含结论。

bug:
- <现象 / 报错 / review finding>

以这些文档或契约为准：
- <contract / architecture / issue 文档路径>

预期行为：
- <应该发生什么>

非目标：
- <这次明确不做什么>

改动范围：
- <允许修改的模块 / 文件范围>

验证：
- <最小测试 / 手工验收 / 命令>

要求：
- 单问题
- 最小改动
- 最小验证
- 修完后说明根因
```

这套模板的核心价值是：

- **先重建边界**
- **再进入修复**

### 3.6 一个真实 bad case：U6 为什么会明显慢于 U1~U5

这次开发里，U6 的执行速度明显慢于 U1~U5，甚至比 U1 和 U5 加起来还慢很多。

根因不在于“前端天然更慢”，而在于我没有把 U6 当成一个收敛的单 Issue 来执行，而是把它做成了一个小型 Sprint。

U6 原本应该只落两件事：

- frontend runtime adapter
- thread shell

但实际实现时，我同时展开了太多不确定面：

- assistant-ui 的选型和接法
- Plane message 到 UI message 的适配
- SSE 流式消费
- 新会话创建时机
- 历史恢复
- 路由接入
- 错误回滚策略

这已经不是“一个最小开发单元”，而是在同一个 Issue 里并行解决多个问题，所以实现速度和收敛性都会明显变差。

进一步看，具体有 5 个直接原因：

1. **一次打开了太多不确定面**  
   我没有把边界压缩到单一问题，而是把“库接入、协议适配、交互时机、错误策略、路由恢复”一起处理，导致每推进一步都要同时校验多个假设。

2. **没有先锁死最小 happy path**  
   正确顺序应该只是先确认：
   - 进入页面
   - 发一条消息
   - 流式显示
   - 刷新后能恢复

   但我在实现过程中还同时决定交互策略，例如：
   - “New chat” 是否立即创建 conversation
   - 首条消息失败后是否删空线程
   - 什么时候跳转到 `/:conversationId`

   这些决策一边做一边定，必然导致反复回看和回退。

3. **对新库边界不熟，却没有先做足够小的 spike**  
   对 `assistant-ui` 这类新接入库，正确做法应该是先用一个 30 分钟级别的最小实验，只验证下面 3 件事：
   - `useExternalStoreRuntime` 能不能接 Plane 的消息结构
   - `Thread` / `Message` / `Composer` 的最小组合能不能工作
   - `submitMode`、`isRunning`、消息更新这些关键行为是否符合预期

   这次我是边接边确认，把探索成本直接叠在主实现里了。

4. **把工程补强混入了主线 Issue**  
   我把一些“有价值但不属于 U6 主线”的处理也一起做了，例如：
   - 首发失败删除空 conversation
   - list 接口兼容数组和 `{ results }`
   - 错误归一化
   - 会话恢复后的状态同步细节

   这些事情不是不该做，而是不应该和“主链路落地”放进同一个高不确定性 Issue 里做。

5. **反馈回路用得太重**  
   U1~U5 主要是后端闭环，契约更稳定，验证路径更直接。  
   U6 我用了更多跨层验证：types、lint、build、runtime 行为确认、路由确认。  
   但更关键的问题不是“验证太多”，而是我没有先建立一个更快的局部反馈回路，再做最终全量验证。

一句话总结根因：

**我没有严格执行“一次只推进一个不确定面”的原则。**

也因此，U6 从“一个 issue”变成了“多个小问题并行求解”，速度和收敛性自然都会变差。

几个很具体的信号，说明当时已经开始发散：

- 开发过程中才发现 `conversation list` 的真实返回并不是文档里的 `{ results }`
- 最后又补修了 `submitMode` 和页面文案不一致
- review 时才暴露出“首发失败可能误删真实线程”的风险

这些信号共同说明：进入实现之前，U6 的边界并没有被压缩到足够小。

这次复盘后，后续执行方式要明确改成下面几条：

- **先做最小纵切面，再做边缘策略**  
  先跑通 happy path；失败回滚、空线程清理、导航优化等都后置。

- **对前端接库类任务先做 30 分钟 spike**  
  只验证 API 和边界，不直接进入完整实现。

- **一个 Issue 内不同时解决“功能 + 交互策略 + 工程补强”**  
  三者必须拆开，至少在心智模型上拆开。

- **先局部验证，再全量验证**  
  先快速确认单页可用，再跑全量 type、lint、build。

这个案例的核心结论不是“前端慢”，而是：

**高不确定性前端任务如果没有先锁死最小主链路，就会在实现中不断吸收新决策，最终把单 Issue 做成多问题并行求解，速度和质量都会一起下降。**

## 4. 提高约束力的关键

仅靠“提醒大家注意收敛”是不够的，必须把约束放进流程里：

- 用 Sprint 模板固定目标、范围、非目标、验收标准
- 用 Issue 模板固定交付物、影响范围、验证方式
- 用 Review 作为进入下一步前的必经关口
- 用“建议去做”清单承接非必要优化，避免顺手扩展
- 用测试、截图、日志等证据确认任务完成，而不是只凭感觉

规范只有进入流程，才真的有约束力。

## 5. 我的结论

如果想提高 AI 代码开发的稳定性，不是让 AI 一次想得更大，而是让它每次做得更小、更清楚、更可验证。

可以把这个方法总结成一句话：

**Sprint 保证方向，Issue 保证聚焦，Review 保证纠偏，“建议去做”负责承接临时想法。**
